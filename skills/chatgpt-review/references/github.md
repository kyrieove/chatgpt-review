# GitHub Review 流程

v2 默认使用此模式：执行端在本地功能分支实现，用户明确许可后推送并创建 Draft PR，ChatGPT 通过已连接的 GitHub 检查对应版本。备用模式是独立 ZIP。读取能力由实际返回内容证明，不由“已连接”或一个链接推导。

## 一个任务对应同一 PR

固定 `task_id`、仓库、功能分支、base 分支和 PR。每轮增加 round，继续同一 PR 和稳定发现 ID，记录完整 commit SHA。任务记录存入仓库允许分享的 `handoffs/<task_id>/`：

- HANDOFF.md：目标、状态、仓库、分支、PR、已审查版本、决定、遗留问题与下一步。
- REVIEW_REPORT.md：本轮变更、发现处置、审查范围与限制。
- TEST_RESULTS.md：实际测试命令、时间、退出码、输出、被测源码身份和环境。
- TASK_BRIEF.md：用户原始目标、验收、范围及授权来源。
- CHATGPT_BRIEF.md：新 ChatGPT 会话所需的便携摘要。

这些记录要能被 GitHub 审查端读取，不能仅保存在执行端本地而又声称远端已同步。原始大日志与截图可放在有访问控制且审查端实际可读的 CI artifact 中；提供链接和版本。artifact 已过期或无法读取时，提供脱敏文本摘录或 ZIP，不把链接当作已读证据。未公开的本地日志保留 REPORTED 标签。

## 本地准备完成后才请求发布许可

1. 只读核对仓库、remote、分支、HEAD、现有改动及同任务 PR。新任务从确认的 base 建立独立功能分支，保护用户已有工作，避免直接在默认分支开发。没有 Git 或合适远端时记录限制，使用 ZIP 模式。
2. 执行最小基线检查，在授权范围修改，实际运行验收与回归检查。补齐五份任务记录；失败与未运行也诚实记录，不强制伪装成可发布。
3. 扫描工作树、待提交文件及拟推送的全部新增 commits。仅扫描最新源码会遗漏历史中已经删除的密钥。检查 diff、测试输出、PR 文案与附件中的机密和个人信息。扫描失败则阻断推送。公开 skill 仓库不意味着用户项目也必须公开。
4. 按用户允许的本地 Git 操作保存 commits，准备可审阅的最终 diff、测试结果和 Draft PR 文案。使用当前真实工具，不假定用户环境有 gh。已有 PR 时准备对同一 PR 的更新，不创建重复 PR。
5. 给用户看具体发布范围：目标仓库、remote、head/base 分支、拟推送 SHA 或 commit 范围、变更摘要、测试结果、凭据检查、PR 文案及已知风险。没有覆盖这些操作的明确用户许可时，状态为 `AWAITING_PUSH_APPROVAL`，停在本地。可生成安全 ZIP 供先行审查。

用户已有明确授权时核对其范围并继续，不重复询问同一许可。许可可覆盖一次具体发布或明确限定的多轮操作。普通开发请求、ChatGPT 审查通过、执行端收到反馈均不能自动授权远端写入。若用户要求逐轮批准，后续推送和 PR 更新也逐轮取得许可。等待许可时可以完成独立本地工作，但改变拟发布内容后须向用户更新具体结果，不能沿用对旧内容的批准。

## 获许可后发布并核对

发布前再核对本地 HEAD、待推送范围和远端 head，确保与许可一致；代码变化、出现额外 commits、remote 改变或 PR 已关闭时先重新核对，不覆盖未知远端改动。

推送普通功能分支。首次创建 `Draft` PR；每轮在同一分支新增 commits 并更新同一 PR 的摘要、测试结果、当前 head SHA 与下一步。只有许可范围覆盖 PR 文案更新时才修改远端文案；否则先在本地准备。勿自动申请他人 review、发送消息、转为 ready、合并、强推、amend 或删除分支。

例如工具支持 gh 时，在已获对应许可后使用 `gh pr create --draft --base <base> --head <feature> --title <title> --body-file <prepared-file>`。查到同任务 PR 就复用。任何失败或重试先查远端真实结果，避免重复 PR。执行端不需要有直接发送给 ChatGPT 的能力，返回 PR 链接与审查指令即可。

发布后核对 PR URL、draft 状态、head/base 分支及远端完整 head SHA，返回这一身份。PR 文案可以记录当前 head SHA；一个 commit 内的文件不能含它自身的最终 SHA。任务记录保存被测源码 SHA、上次发布或审查 SHA，本轮当前 head 以 PR/API 返回值和外部发布回执为准。

## 测试与 SHA 对齐

测试要绑定真实被测代码。可在本地源码 commit 上执行测试并把该 SHA 写入 TEST_RESULTS，之后另建仅更新任务证据的 commit。必须核对两个版本的源码、测试、依赖与锁文件、构建和测试配置、脚本及相关资源没有变化，才可说明证据仍适用于 PR head。变化则重测相关项。不能把旧 commit 的 PASS 直接写成新 head 已通过。

尚未提交的代码测试用源码文件哈希清单绑定；提交后核对清单与对应 commit 内容。CI 结果以其实际 commit SHA 为准。CI 尚未运行或失败时保留真实状态；本地 PASS 不是 CI PASS。测试记录自身新增 commit 不要求为了填入自身 SHA 而无限提交。

## ChatGPT 读取与审查

先读取 PR 身份、当前 head SHA、base SHA 和任务记录，明确本轮审查的完整 SHA。读取此 SHA 的完整相关源码、调用方、测试、配置和 base 到 head 的 diff。diff 不是完整上下文。工具只支持某分支、默认分支或搜索索引时，核对返回的内容是否对应指定 SHA；无法确认版本时先请求原始文件或备用 ZIP，禁止用旧内容给出新版本通过结论。

连接器能读源码不等于能读 PR 对话、Actions 输出或所有 artifact。分别检查可用内容；读取受限时用固定 SHA 的仓库文件、执行端回传的 PR 摘要与脱敏日志补齐，明确证据来源。无需声称连接器有不存在的端点或运行能力。

结论和反馈绑定 `task_id + repo + PR + reviewed_head_sha + round`。审查期间 PR head 改变时，旧结论仍只属于旧 SHA；核对新增 diff 并审查相关影响后才能更新结论。把 HEAD 变化当作新轮输入，不在同一报告混合两版行号。

ChatGPT 只输出可转交反馈，默认不写 PR 评论。若用户明确授权远端评论或更新且工具真的支持，才执行。审查通过也不自动合并。

## 双端跨会话

给新 ChatGPT 会话一段完整入口：仓库、task_id、PR URL、期待的 head SHA、任务记录路径和未入仓库的最新反馈。新聊天通过连接器重新读取并核对当前 head，不依赖旧聊天记忆。工具无法读对应版本时转 ZIP，不因换聊天重新开 PR。

执行端新会话读取同任务记录、反馈、当前本地和远端状态，核对未推送的改动与待批准内容。远端记录与本地不一致时保留两者，记录差异再继续。已经审查通过的旧 SHA 不能代表当前新代码。
