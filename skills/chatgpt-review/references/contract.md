# 任务记录与备用 ZIP 契约

v2 默认 GitHub Review，其 PR、完整 SHA 与用户许可流程见 github.md，备用包内副本为 GITHUB_REVIEW.md。下面的 package_id 与压缩预算只用于 ZIP，不替代 GitHub 的 reviewed_head_sha。

## 身份与持久记录

`task_id` 标识同一项用户任务，创建后不变。`round` 是该任务的递增正整数。`package_id` 标识一次打包，重新打包也使用新 ID。修复轮沿用 task_id；不同目标另开任务。打包工具只记录传入的 round，执行端负责核对它大于已交付轮次，不能把旧轮次当作最新版本。

默认任务目录 handoffs/<task_id> 是执行端维护的权威记录。GitHub 模式如该目录被忽略，可选择用户允许跟踪的记录目录，并在任务入口及 PR 写明实际路径。根 HANDOFF 只做指针，已有他人管理的同名文件保持原样。可选 ZIP CLI 仍按 handoffs/.current-task 定位默认任务；其他记录路径需手动按相同契约打包。审查包总会生成专用根指针。

HANDOFF 的状态使用 PLANNING、EXECUTING、AWAITING_PUSH_APPROVAL、READY_FOR_REVIEW、NEEDS_FIXES、BLOCKED、DONE。状态是核实后的记录，不由打包、测试或推送成功自动推导。状态、任务 ID、round、决策版本与输入 SHA 或包身份应一致。

## 一包可以独立继续

```text
<task_id>-r<round>-<unique>.zip
├── CHATGPT_START.md             ChatGPT 使用说明
├── REVIEW_PROTOCOL.md           本交换契约
├── GITHUB_REVIEW.md             GitHub 模式与许可流程
├── PACKAGE_INFO.json            包身份、范围、Git 情况及排除项
├── SHA256SUMS.txt               除自身外每份文件的 SHA-256
├── HANDOFF.md                  本包任务指针
├── handoffs/<task_id>/
│   ├── TASK_BRIEF.md            用户目标与已授权任务书
│   ├── HANDOFF.md               当前状态、决定、遗留问题、下一步
│   ├── REVIEW_REPORT.md         变更、验收、命令与证据
│   ├── TEST_RESULTS.md          测试输出、被测源码身份及凭据扫描
│   ├── CHATGPT_BRIEF.md         新 ChatGPT 聊天所需摘要
│   ├── feedback/               已收到的原始反馈与处理记录，如有
│   └── logs/                   原始输出与相关截图，如有
└── <项目相关源码、配置、测试、锁文件与必要资源>
```

没有 Git 时明确记录不可用，通过报告描述变更。存在 Git 时包含 HEAD、分支、状态、已暂存和未暂存 diff；没有已提交基线时不要伪造基线。已提交的任务改动仍须报告基线及相应 diff，不仅检查工作区 diff。打包工具默认仅采集当前工作区 Git 信息，执行端按任务需要另存基线 diff。

自动 Git 状态和 diff 仅包含指定项目中符合本包选定范围与分享过滤规则的路径，不提供被排除文件或项目外目录的改动。二进制内容不嵌入补丁。过滤后为空不能证明整个仓库没有未提交改动；执行端在本地核对真实状态并报告与任务有关的限制。

源码范围须足够解释验收行为，包括新增和未跟踪文件、相关调用方、依赖声明和资源。明确包里哪些内容不提供，为什么不提供，是否妨碍审查或运行。默认打包采用过滤后的项目快照；并不保证包含一切。`--include` 是替换默认选择的范围，仍会加入当前任务记录。含排除项或只选部分路径时不得声称完整快照。

显式选择单个文件意味着该文件必须实际入包：敏感、超限、不可读取或其他过滤原因会直接失败，不生成最终 ZIP。选择目录则允许过滤其中子项并记录遗漏。失败不能通过放松安全规则来修复，只能更正选择或提供安全材料。

`PACKAGE_INFO.json` 至少包含 `schema_version`、`task_id`、`round`、`package_id`、`created_at`、Git 可用情况、`selection_scope`、`skipped_paths`、`full_snapshot` 和测试执行说明。SHA256SUMS 对复制进包的实际字节计算。元数据的来源与测试报告版本应可核对；哈希不是测试认证。

每轮携带完整当前记录与选定源码，不能只发 diff，也不能要求审查端回看旧附件。大型项目可分卷上传并共享包身份、文件索引与相对路径；用户未传齐时仅审查已收到部分。只有修改文件、没有接口上下文的包不能支持完整行为验收。

## 控制每轮大小

审查包按当前工作项取材，不随轮次叠加所有历史。例行修复用 `--include` 选择完整相关源码、调用方、接口、测试、依赖声明与必要资源；首轮调查或明确要求全量审查时可以使用默认项目快照。选择的是可独立解释当前验收的范围，不是只选修改行。

用重复的 --evidence 选择本轮证据与仍需核对的反馈，例如 --evidence logs/round-3 --evidence feedback/round-2.md。五份任务记录总会加入。未指定 evidence 时工具保留当前任务的全部可分享材料，因此长期任务应显式选证据。

旧已解决发现、旧决策与尝试结果压缩为 HANDOFF 和 CHATGPT_BRIEF 中的事实摘要，保留稳定发现 ID、结果、依据及轮次。原始文件仍在本地，不自动删除。未解决问题必需的旧证据仍选入；报告引用的本轮证据必须能在包中找到。被省略的历史只可视为执行端报告，不是 ChatGPT 已直接检查的材料。需要复核时重新收集并上传。

每包保持独立，换聊天无需旧 ZIP。默认排除旧 ZIP、其他任务和依赖缓存。一次生成新 ZIP，不在旧 ZIP 上追加内容。回归问题涉及其他模块时扩大相关范围，不能为减小体积隐藏关键上下文。

`--max-package-mb` 控制压缩后 ZIP 的硬预算，默认 25 MiB，这是本工具的工作预算，不是 ChatGPT 的平台上传限制。上传限制由当前聊天平台决定，可以设置更小的预算。超预算停止生成新的最终 ZIP，报告体积和大文件名单，执行端重新选择闭合范围、精简重复证据，或安排有索引的分卷上传；不能静默截断文件、删掉失败日志或把部分审查标为完整。

## 反馈和目标变化

反馈存入 feedback，文件名使用轮次和输入 package_id 或 reviewed_head_sha，保留原文与处理结果。反馈绑定对应版本。发现 ID 跨轮稳定，关闭需要新证据，延期需要理由与用户接受记录。

目标改变时更新 TASK_BRIEF 的决策版本、目标差异与验收；保留旧决定的简短历史。执行端在新包带上最新目标。ChatGPT 不凭执行端自行扩大目标的说法确认用户授权。

并行工作项各自保存结果，由一个指定执行端整合任务状态和最终包。拆分为独立用户任务时使用不同 task_id，记录依赖。无共享写入能力时使用人工转交，不虚构后台协作。

## 分享前检查

排除密钥、环境变量文件、认证会话、用户私有数据、数据库、依赖缓存和构建缓存。扫描源码、日志、diff、元数据与截图。文件名过滤和 token 模式扫描仅为辅助，执行端仍需检查个人信息及商业保密内容。不要为通过扫描自动改动用户源码或隐藏真实测试失败。

必要敏感材料用脱敏副本或接口描述替代，报告它造成的验证限制。发现疑似凭据时阻断打包，不生成可分享 ZIP；安全处理后用新 package_id 重打包。失败测试仍可以安全打包，测试失败与隐私阻断是不同结果。

## 可恢复的下一步

执行端续接需本地任务记录与项目。ChatGPT 优先重新读取同一 PR 和远端记录，核对完整 SHA；无法读取时上传最新独立包及尚未保存的反馈。两端写全状态与下一步，不依赖聊天记忆。
